# Host-wide daily check-ins

The Host service uses the zss.pub SQL HTTP API with a Host-only API key and a configured database UUID/two physical table names. No SQLite or removed records API fallback remains. Agent tools and generated Remote methods share asynchronous operations. Topics have id, name, created_at, updated_at and revision. Daily records have topic_id, date, created_at and revision, primary key (topic_id, date) and index (date, topic_id). UUIDs and ISO timestamps are generated by the Host. Dates remain canonical VARCHAR strings to support years 0001–9999.

The service initializes its store lazily on the first check-in request. Invalid or missing database credentials return a typed configuration error at that boundary without preventing the Host/plugin tree from starting. Failed initialization is not cached. Disposal cancels an initialized store and prevents later initialization; cancelled requests do not initialize storage.

UI-only connection/login/resources/connect/initialize/logout Remotes manage a versioned grant record in ctx.credentials under dsh-checkin/connection. Credentials are never returned; external key/UUID configuration takes precedence as a unit and cannot be changed by the page. Login only verifies database read access. Initialization requires confirmation, checks live quotas and schema, preserves partial resources, and never retries uncertain writes or rolls back by deletion. All connection and business operations share a local queue. Saved revisions protect record replacement from competing writers; logout uses the provider's explicit deleteRecord operation, not modifyRecord(undefined), which is a no-op.

A page-shared connection controller invalidates each calendar controller on connection changes. Visible tabs recheck the Host state before fetching calendar data; stale requests are cancelled and discarded. Keys exist transiently in the form and authenticated submission only, never browser storage or model tools. Default Host credential storage is an owner-only file, not encryption or isolation from the same OS user.

Topics have no start date. Any historical date can be completed, and overview denominators use the current catalog. Topics require primary id and unique name indexes. Rename checks topic revision. Completion uses a conditional INSERT SELECT from the parent; undo deletes one record with its previous revision. One guarded multi-table DELETE removes topic and records together, reporting actual affected rows minus one. The service serializes SQL under its user lock. This protects cooperating writers, not arbitrary external edits. There are no foreign keys or cross-request transactions.

Readers use cancellation and refuse late results. UI writes serialize and refresh after success; visible tabs poll every 30 seconds by default. Reads check overview and both schemas, then paginate topics by id and date-filtered records by (date, topic_id), LIMIT 100. Exact COUNT(*) before and after is parsed without Number precision loss; estimated overview recordCount is ignored. The catalog is rechecked after range reads. This is not a transactional snapshot.

Incompatible schemas, including completed_dates even when nullable, are refused. Saved version-1 connections return to setup; version 2 persists both names. Initialization creates topics through structured columns and records through SQL DDL for the composite primary key; existing tables must be explicitly selected and validated before creating a missing partner. Both table slots are preflighted. Physical-name remapping and historical migration are not automatic. Live usage at/above maxBytes blocks INSERT and all UPDATEs; undo and topic removal use DELETE and remain allowed without claiming page reclamation. HTTP 413 means request/result size, not storage quota. Writes recheck schema, overview and data and never retry automatically. SELECT POST failures remain read failures; write timeouts are uncertain outcomes. The service origin is fixed and credentialed redirects are prohibited.
